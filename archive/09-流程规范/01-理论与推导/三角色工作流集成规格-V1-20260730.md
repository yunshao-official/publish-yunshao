## 一、职责边界精确定义

### 1.1 证明官 vs 计算员

| 维度 | 计算员 | 证明官 |
|------|--------|--------|
| 核心动作 | **跑数值**（给定公式+输入→输出结果） | **验公式**（给定推导链→检查代数/量纲/定义域） |
| 输入 | 公式+参数+精度要求 | 推导链+声称结论+来源文档 |
| 输出 | 数值结果+复现脚本 | 验证报告（✅/❌/⚠️+证据） |
| 工具 | Python/Node数值计算 | 代数推导+独立复算+量纲分析 |
| 判据 | 数值精度（小数点后N位） | 逻辑正确性（每步推导是否合法） |

**边界裁决（"跑数值验证公式对不对"算谁的？）：**
- 若任务是"给定公式f(x)=x²，算f(3)=?"→**计算员**（纯数值执行）
- 若任务是"文档声称f(x)=x²的导数是2x，验证对不对"→**证明官**（验证推导正确性）
- 若任务是"文档声称Σ(1/n²)=π²/6，用数值验证"→**计算员先跑数值**（得到1.6449...）→**证明官判"数值一致≠证明成立"**（数值验证是必要非充分条件）
- **裁决规则：涉及"对不对/为什么/推导是否合法"→证明官；涉及"算出来是多少"→计算员。两者可串联（计算员跑数→证明官判逻辑），不可互相替代。**

### 1.2 文献员 vs 工程师

| 维度 | 工程师 | 文献员 |
|------|--------|--------|
| 核心动作 | **改内容**（代码/文档的实质修改） | **管生命周期**（索引/版本/归档/检索） |
| 写权限 | 可写（限指定输出路径） | 可写（限索引文件/归档操作） |
| 理论内容 | 可改（按任务书） | 不可改（铁律10） |
| §十回写 | **工程师负责**（R14：改代码必回写§十） | 文献员**检查**§十是否已回写（不代写） |

**边界裁决（"文档与代码对齐"谁负责？）：**
- **工程师**：改代码后回写§十（R14铁律）→这是"改"的动作
- **文献员**：验收时检查§十是否已回写、版本号是否对齐、旧版是否标记作废→这是"管"的动作
- **裁决规则：谁改谁回写（工程师）；文献员只做一致性检查+告警，不代写不代改。** 若文献员发现§十未回写→告警主agent→主agent派工程师补写→文献员复查。

### 1.3 元改进 vs 审查官

| 维度 | 审查官 | 元改进 |
|------|--------|--------|
| 核心动作 | **查"做了什么"**（每日审agent交付物/铁律/摸鱼） | **查"流程本身对不对"**（识别系统性问题模式） |
| 频率 | 每日22:00（cron自动） | 按需（审查官报告后/主agent派/R17跑完后） |
| 输入 | 当日session记录+交付物 | 多日教训记录+审查官报告+流程执行日志 |
| 输出 | 审查报告（逐agent·五查） | 流程改进报告（模式+根因+提案） |
| 权力 | 可标红/告警/建skill提案 | 只提建议（知世批了才改） |

**边界裁决（"审查官自己漏审了"谁发现？）：**
- **元改进**负责发现审查官漏审。机制：元改进定期（**每3天**或**每完成一个R17完整流程后**，取先到者）读审查官报告+实际session记录→交叉比对→若发现"某agent连续N天无审查记录"或"某类错反复出现但审查官未标红"→输出告警。
- **裁决规则：审查官审agent，元改进审审查官（+审流程本身）。** 这是"谁审审查者"问题的解：元改进是审查官的审查者，但元改进不替代审查官的日常职能。
- **兜底：主agent（聆星/熵墟）每3天读一次元改进报告，确认审查官覆盖率。** 若元改进也不可用→主agent自己兜底（降级策略§五）。

## 二、调用时机（触发条件）

### 2.0 "不确定"的操作定义（P1-2修）

以下三条满足任一即判定"数学声明不确定"，触发证明官验证：

| # | 判据 | 说明 |
|---|------|------|
| (a) | 文档中该声明标有⚠️或❌ | 已有标记=已知存疑 |
| (b) | 攻击手/发现者在30秒内无法独立验证 | 不能秒验=需要专门验证 |
| (c) | 涉及常数互锁（α/η/κ/ε/Λ_ord中≥2个同时出现） | 常数互锁=错一个全链错，强制验证 |

**不满足以上三条=确定，不触发证明官。** 防止"什么都派证明官"导致调度爆炸。

### 2.1 自动触发（无需主agent手动派）

| 角色 | 触发条件 | 嵌入R17阶段 |
|------|---------|------------|
| 证明官 | 攻击手在②攻防中发现数学声明不确定（§2.0判据）→攻击手直接派证明官验 | ②攻防设计（辅助） |
| 证明官 | ⑦验收交付时，计算员跑数结果与声称值偏差>阈值→自动触发证明官复核 | ⑦验收交付（辅助） |
| 文献员 | ④基线锁定时，自动检查文档版本与代码版本对齐 | ④基线锁定（辅助） |
| 文献员 | ⑦验收交付时，自动检查§十是否已回写 | ⑦验收交付（辅助） |
| 元改进 | 每日审查官出报告后→元改进自动读报告→识别系统性问题 | 日常维护（横切） |
| 元改进 | R17完整流程跑完后→元改进自动检查是否有步骤被跳过 | 经验总结（横切） |

**⚠️ P0-2修·自动触发阈值（待知世确认）：**

⑦验收交付时"偏差>阈值"的定义：
- **相对偏差 > 1%**（|计算值−声称值|/|声称值| > 0.01），或
- **绝对偏差 > 0.01**（|计算值−声称值| > 0.01，当声称值接近0时兜底）
- 两者取OR（满足任一即触发）
- **⚠️ 此阈值为工程师建议值，待知世确认。确认后写入规格不可改，变更需走R17流程。**

### 2.2 手动触发（需主agent派）

| 角色 | 触发条件 | 谁派 |
|------|---------|------|
| 证明官 | 任何agent发现数学声明不确定（§2.0判据·非攻防阶段） | 发现者→报主agent→主agent派 |
| 文献员 | 知世说"这个作废"/"找某份文档"/"查某常数在哪些文档出现" | 主agent派 |
| 文献员 | 新文档入库（H:\理论存档\新增文件） | 主agent派（或工程师改完后通知） |
| 元改进 | 主agent发现某类错反复出现（≥2次） | 主agent派 |
| 元改进 | 新技能提案提交后→审查是否与现有技能冲突/重复 | 主agent派 |

### 2.3 并发冲突处理（P2-3修）

**场景：证明官和攻击手同时被派验同一个东西，结果矛盾。**

**裁决规则：**
1. **证明官验"对不对"（数学正确性），攻击手验"有没有漏洞"（工程/逻辑完备性）。** 两者维度不同，矛盾通常是伪矛盾（一个说"公式对"，另一个说"公式对但适用条件不满足"）。
2. **若证明官✅，攻击手❌：**
   - 攻击手❌的理由是"工程不可行/实现有漏洞"→攻击手❌降级为⚠️，以证明官✅为准（数学对，工程另议）
   - **攻击手❌的理由是"前提/定义域不满足"→不降级。** 证明官✅与攻击手❌并列，主agent/知世裁决。（P2-3修：定义域问题是数学问题，不是工程问题，攻击手在此维度有发言权）
3. **若证明官❌，攻击手✅：** 以证明官为准（公式错就是错，攻击手不验数学）。攻击手的✅视为"未检查数学正确性"。
4. **仲裁者：主agent。** 两者结果矛盾→主agent读两份报告→判断是伪矛盾还是真矛盾→真矛盾交知世裁决。

## 三、输出格式与交接（P1-1修·R19合规）

### 3.1 证明官·验证报告

```
## 验证报告
- 声明：{被验证的数学声明}
- 来源：{文档路径+行号}
- 方法：{独立复算/代数检查/量纲分析/统计检验}
- 结果：✅通过 / ❌不通过 / ⚠️有条件通过
- 偏差：{具体数值·若有}
- 证据：{计算过程·关键步骤}
- 复现信息：{脚本路径/依赖版本}
- 交接：→ {主agent/攻击手/工程师}（谁派的回谁）

## 决策链
- 决策：{验证方法选择·判据选择}
- 理由：{为什么用这个方法·可证伪判据"若P则结论不成立"}
- 依赖：{依赖的公理/常数/定义·到§级}

## 未选路径
- {未用的验证方法+为什么不选}
```

### 3.2 文献员·文档操作报告（R19豁免）

```
## 文档操作报告
- 操作：{索引更新/版本归档/一致性检查/检索结果}
- 文件：{完整路径}
- 变更：{具体改了什么}
- 影响：{哪些agent/文档受影响}
- 验证：{机器校验结果·若有}
- 交接：→ {主agent/工程师}（谁派的回谁）
```

> R19豁免理由：文献员报告是纯操作记录（改了什么/影响谁），不含决策/否决/方案选择，不满足R19"任务书必带决策链"的适用条件（豁免：纯查询/单文件微调）。

### 3.3 元改进·流程改进报告

```
## 流程改进报告
- 观察：{什么问题模式}
- 证据：{哪些教训/哪些session/重复几次}
- 根因：{为什么会反复出现}
- 提案：{具体改什么·改哪个文件·改成什么}
- 影响范围：{哪些agent/规则/技能受影响}
- 验证方法：{怎么确认改完有效}
- 交接：→ 主agent（所有提案必须经主agent→知世批准才落盘）

## 决策链
- 决策：{提案方向选择}
- 理由：{为什么选这个方案·可证伪判据"若P则提案不成立"}
- 否决：{被否方案名+具体缺陷}
- 依赖：{依赖的铁律/规则·到§级}

## 未选路径
- {未选的改进方向+为什么不选}
```

### 3.4 交接规则（P2-1修）

**原则：谁派的回谁（不越级）。**
- 主agent派→回主agent
- 攻击手派证明官→回攻击手（攻击手汇总后进攻防报告）
- 工程师派文献员→回工程师（工程师确认后进交付物）
- 审查官触发元改进→元改进回主agent（审查官不直接改流程）

**P2-1修·告警级直接通信（例外）：**
- 允许：文献员→证明官发送**告警级验证请求**（场景：文献员做一致性检查时发现同一常数在不同文档中值不一致→直接请求证明官验证哪个值对）
- 允许：证明官→文献员发送**告警级检索请求**（场景：证明官验证时需要查某常数的原始定义出处→直接请求文献员检索）
- **限制：仅限告警级（发现矛盾/不一致时的即时请求），不允许任务级互派（不许"帮我做XX"）。**
- **结果仍回主agent：** 直接通信的结果（验证结论/检索结果）必须同时抄送主agent。主agent是信息汇聚点。
- **延迟对比：** 原4跳（文献员→主agent→证明官→主agent→文献员）→现2跳（文献员→证明官→抄送主agent）。

**P1-1修·告警级操作定义（V2.1新增）：**

| 级别 | 操作定义 | 形态 | 示例 |
|------|---------|------|------|
| **告警级**（允许直接通信） | 单一常数在两份文档中值矛盾 | **1对1**（一个常数·两份文档） | "η在文档A=7/8、文档B=5/6，验证哪个对" |
| **任务级**（禁止直接通信·走主agent） | 批量检查/多文档扫描 | **1对N**（多个常数或多份文档） | "扫描H:\理论存档\全部文档检查常数一致性" |

**告警级每日上限：5次（每对发送方→接收方）。** 超过5次→判定为批量任务→转主agent统一调度（防止把批量任务包装成"告警"淹没接收方）。主agent在当日memory记录直接通信次数。

**禁止：** 任务级互派（"帮我写XX/帮我改XX"）。所有跨角色任务协调经主agent。

### 4.2 调用链示例


## 五、降级策略（P0-1修）

### 5.1 证明官不可用

| 降级层级 | 替代者 | 能力损失 | 恢复条件 |
|---------|--------|---------|---------|
| L1 | **计算员跑数+攻击手判逻辑（串联）** | 计算员不判逻辑，攻击手不跑数→串联覆盖但延迟增加 | 证明官恢复后补验 |
| L2 | 主agent标记"⚠️数学验证待补"→不阻塞流程但标红 | 验证缺失·风险累积 | 证明官恢复后必须补验所有标红项 |

> **P0-1修·删除原L1"计算员代验"：** 计算员是执行者，代验=执行者做验证者，违反R17权力分立（研发≠验证）。新L1改为串联：计算员只跑数（执行），攻击手判逻辑（验证），两者角色不混。若攻击手也不可用→直接跳L2标红。

**触发条件：** sessions_send超时（>120s无响应）或provider限流。
**铁律：** 降级不免除验证义务——标红项必须在24h内补验，否则主agent告警知世。

### 5.2 文献员不可用

| 降级层级 | 替代者 | 能力损失 | 恢复条件 |
|---------|--------|---------|---------|
| L1 | 工程师代管（索引+版本检查） | 工程师可能改内容时顺手改索引→权力不分离 | 文献员恢复后复查 |
| L2 | 主agent代管（检索+一致性检查） | 主agent时间成本高·不专业 | 同上 |
| L3 | 跳过文献员步骤·标红"文档一致性待查" | 旧版污染风险·索引失准 | 文献员恢复后全量扫描 |

**触发条件：** 同证明官。
**铁律：** 归档操作（不可逆）在文献员不可用时**冻结**——不许降级执行归档。只有检索/检查可降级。

### 5.3 元改进不可用

| 降级层级 | 替代者 | 能力损失 | 恢复条件 |
|---------|--------|---------|---------|
| L1 | 审查官代审流程（在每日审查中加"流程完整性"一栏） | 审查官视角是"做了什么"不是"流程对不对"·深度不够 | 元改进恢复后补审 |
| L2 | 主agent代审（每3天读一次教训记录） | 主agent时间成本高·可能遗漏模式 | 同上 |
| L3 | 跳过·标红"流程改进待补" | 同类错可能继续重复 | 元改进恢复后必须补审所有标红期间 |

**触发条件：** 同上。
**铁律：** 元改进不可用时，新技能提案的"冲突/重复审查"由主agent代做（不冻结，因为技能提案不阻塞主流程）。

### 5.4 私有内容读取边界（P1-2修·V2.1新增）

文献员/元改进因职能需要读取其他agent的MEMORY.md/session记录，但其中含密钥路径/教训/知世私密对话。读取边界写死：

| 角色 | 可读 | 禁读 |
|------|------|------|
| **文献员**读MEMORY.md | 仅限"常数速查/索引/版本记录"段 | **不读"教训/密钥/私有"段** |
| **元改进**读session | 仅限"流程执行日志"（哪个agent被派了什么任务/结果如何/耗时） | **不读任务内容/知世对话/理论实质** |

- 文献员做一致性检查只需常数值+版本，不需教训/密钥。越界读=信息泄露=失职。
- 元改进做流程分析只需"谁被派了什么/结果如何"，不需任务的具体理论内容。越界读=侵犯隐私=失职。
- **技术保障：** 读取时按段标题定位（grep段头），不整文件灌入（铁律·token节约）。若目标文件无明确段标题→只读文件头部索引区，不读全文。

### 5.5 降级通用规则

1. **降级必须留痕**：主agent在当日memory记录"HH:MM {角色}不可用→降级为{替代者}→标红项：{列表}"
2. **降级不超24h**：超过24h仍不可用→主agent告警知世
3. **降级期间产出标⚠️**：所有降级替代的产出必须标"⚠️降级产出·待{原角色}复查"
4. **恢复后必须补验**：标红项不是"算了"，是"排队等补"
