## 一、病因（三演实录）

**机制**：在 Python 源码里写 `"H:\理论存档\01-数学"`，解释器把 `\01` 当八进制转义，产出控制字符 chr(1)（SOH），**反斜杠和 0、1 三个字符一起被吃掉**，文件里落盘的是 0x01 而不是 `\01`。bash 的 `echo -e`、heredoc 未加引号时同理。

**已实证的产生关系**（2026-09-19~21 三次事故，89 处损伤逐一回查）：

| 源码里写的 | 被解释成 | 落盘字节 |
|---|---|---|
| `\01` | chr(1) SOH | 0x01 |
| `\02` | chr(2) STX | 0x02 |
| `\04` | chr(4) EOT | 0x04 |
| `\05` | chr(5) | 0x05 |
| `\07` | chr(7) BEL | 0x07 |
| `\a` | chr(7) BEL | 0x07 |
| `\b` | chr(8) BS | 0x08 |
| `\v` | chr(11) VT | 0x0B |
| `\0` `\00` `\000` | chr(0) NUL | 0x00 |
| `\202` | chr(0x82) | UTF-8 落盘为 `C2 82`（U+0082，C1 控制字符） |

**危险字符清单**：Python 转义会吃字节的反斜杠序列包括 `\0`~`\7` 开头的八进制（后随 1~3 个数字）、`\a \b \f \n \r \t \v \x.. \u....`。**最阴险的是路径类文本**：Windows 路径 `\01-数学`、`\04-工具与代码`、`\071_xxx`、`\v3_xxx`、交付包名 `\20260919-xxx` 全是雷区。

**三演记录**：0919 哈密顿线写 m1scan 路径（`\v` 被吃）；0920 夜 01 域索引登记（`\01`/`\04` 被吃）；0921 专项清查存量登记件共扫出 89 处（状态广播板 60、文档索引-INDEX 12、daily 11、MEMORY 5、其他 1）。**另有第四演**：在文档里*描述*损伤时写 `\01`，写的时候又被吃一遍——自指再伤（本次修复中 广播板 L708、MEMORY L395 即此类）。

## 二、防御写法：chr(92) 拼接法

**铁律：任何含反斜杠的字符串（Windows 路径、正则、示例文本），禁止字面反斜杠写进 Python/bash 源码。一律用 chr(92) 拼接。**

Python 正例：

```python
BS = chr(92)  # 反斜杠常量，全程唯一来源
path = "H:" + BS + "理论存档" + BS + "01-数学" + BS + "05-索引"
# 或者 bytes 层直写（最稳）：
data = b"H:" + bytes([92]) + "理论存档".encode("utf-8")
```

Python 反例（禁止）：

```python
path = "H:\理论存档\01-数学"        # \01 被吃成 SOH
path = r"H:\理论存档" + "\05-索引"   # r-string 只保护自己这一段，拼错照样被吃
```

bash 正例：

```bash
BS=$(printf '\092' 2>/dev/null || printf '\\')   # 或直接用反引号内单引号包裹
echo 'H:\理论存档\01-数学'                        # 单引号内不转义，安全
```

bash 反例（禁止）：`echo "H:\01-数学"`（双引号+echo -e 场景会把 \01 吃掉）。

**补充**：用 Write/编辑器类工具直接写文件（不经 shell/python 字符串解释层）的，字面反斜杠安全，但写完仍须跑第三节终检。

## 三、写后终检清单（六项，缺一不可）

任何文件写完（尤其登记件、索引件、带路径的 md），立刻跑：

1. **严格 UTF-8 解码**：`data.decode("utf-8")` 零异常；
2. **C0 控制字符**：0x00-0x1F 中除 `\t`(09) `\n`(0A) `\r`(0D) 外零残留（含 NUL=0x00）；
3. **C1 控制字符**：U+0080-U+009F（UTF-8 落盘为 `C2 80`~`C2 9F`）零残留；
4. **NUL 专项**：0x00 计数 =0；
5. **孤立 CR**：0x0D 后面不是 0x0A 的计数 =0；
6. **DEL**：0x7F 计数 =0。

可直接复用的终检代码（bytes 层，无字面反斜杠）：

```python
import sys
def terminal_check(path):
    data = open(path, "rb").read()
    bad = []
    try:
        data.decode("utf-8")
    except UnicodeDecodeError as e:
        bad.append(("INVALID-UTF8", e.start))
    i = 0
    while i < len(data):
        b = data[i]
        if b < 0x20 and b not in (9, 10, 13):
            bad.append(("C0-0x%02X" % b, i))
        if b == 0x7F:
            bad.append(("DEL", i))
        if b == 0x0D and (i + 1 >= len(data) or data[i+1] != 0x0A):
            bad.append(("LONE-CR", i))
        i += 1
    txt = data.decode("utf-8", errors="ignore")
    for ch in txt:
        if 0x80 <= ord(ch) <= 0x9F:
            bad.append(("C1-U+%04X" % ord(ch), txt.index(ch)))
    return bad   # 空列表 = 通过
```

## 五、修复纪律（七条）

1. **只动控制字节**：除控制字符还原外一字不动，语义零改动；
2. **无歧义才修**：上下文+磁盘真值双确认；歧义挂 FIXME；
3. **自指行同修**：描述损伤的文字自身被吃（如"（`\01`→chr(1)）"）同样还原；
4. **bytes 层操作**：带上下文的字节序列精准替换，逐模式计数断言（期望数≠实见数即中止该文件）；

## 六、术语字典

- **转义吃字节**：源码字符串里的字面反斜杠序列被解释器/-shell 当转义符解释，反斜杠连同后随字符一起消失、只剩一个控制字符落盘的故障。
- **控制字符**：Unicode/ASCII 中不可见打印的控制符；C0=0x00-0x1F（含 NUL、SOH、VT 等），C1=U+0080-U+009F（UTF-8 落盘为 C2 80~C2 9F）。
- **chr(92) 拼接法**：用 `chr(92)`（反斜杠的码点写法）构造反斜杠常量再拼接字符串，使源码中不出现字面反斜杠，杜绝转义解释。
- **八进制转义**：Python/bash 中 `\` 后随 1~3 位八进制数字（如 `\01`）产生对应码点字符的语法，是吃字节的主凶。
- **地面真值核验**：还原损伤路径前，先列出磁盘上真实存在的文件/目录名做对照，还原结果必须与磁盘一致。
- **自指再伤**：在文档中描述本故障时写出 `\01` 等示例，写入过程本身又被转义吃掉，形成二次损伤。
- **FIXME 挂账**：无法无歧义还原的损伤点不做猜测性修改，就地插注释行标注偏移与疑似原意，留给人工或后续会话裁决。
- **mtime 避让**：写入前检查文件最近修改时间，10 分钟内有并行会话写入则跳过，防止覆盖他人追加。
- **终检**：文件写后的机械化字节级复查，按第三节六项执行，任何一项不过即返工。
