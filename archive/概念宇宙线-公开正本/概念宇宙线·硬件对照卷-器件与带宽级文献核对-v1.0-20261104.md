## 〇 一句话结论（先给裁决）

1. **她的架构判决（RX 580＝语法门加速器＋解包第二引擎，不是主推理引擎）在硬件算术上成立**，而且比她写的更强：不是"意愿上不让它当主引擎"，是**它当不了**——RX 580 256 GB/s 的显存带宽与 8 GB 显存装不下 18.56 GB 的 30B 门，专家权重必须留在 DDR 侧。文献独立支撑：MoE 冷专家留 CPU、热路径上 GPU 正是 KTransformers（SOSP'25）、PowerInfer（SOSP'24）、EdgeMoE 的标准做法。
2. **"带宽=硬墙"要改口径**。把她的实测数反推成"实际达成带宽"，全部落在 5.6–8.7 GB/s；DDR4-2400 双通道理论 38.4 GB/s。**墙有两层：理论管子（38.4）和实际流到的水（8.7）。她一直在跟第二层打仗，但登记的是第一层的名字。**
3. **最响的报警信号不是慢，是 `prompt处理4.7＝生成4.7`**。按公开文献，prefill 是算力受限、decode 是带宽受限，两者本应差 5–20 倍；两者相等是"IO/换页限制了两段"的指纹——llama.cpp 官方仓库 2026-09 的一份 MoE mmap 报告里，同样的形态（4.6 t/s）被 O_DIRECT 绕过页缓存后变成 16.3–140 t/s。**这条是她最便宜、最可能翻盘的一个实验。**
4. **"加内存条翻倍以上"这句丑话前置里的预期，算术上不支持**（38.4→51.2 只有 +33%）；但如果她当前确实有工作集落在 flex 的单通道溢出区、或长 prompt 反复把专家页挤出页缓存，**换 2×32 GB（不是 2×16 GB）的实际收益可以是 1.5–2×**。她写的方向对、容量档位选小了：18.56 GB 模型 + 3 GB 宇宙 + 1.6 GB KV(16k) + 系统与显存驱动常驻，32 GB 只剩 8 GB 余量，而一次 prefill 扫全 128 专家的足迹是 17.6 GB。
5. **"5012 tok/s 是 552B 直接推理的 5000 倍"这句要拆**。硬件层它不是"架构优越 5000 倍"，是两件可数的东西相乘：**每 token 触碰字节量少约三个数量级**（≈1.7 MB 对 ≈1.85 GB ≈ 1063×），**加带宽源从 NVMe 换成了 DDR**（<1 tok/s 那个数是 768 MB/s 顺序读流的产物，不是算力上限）。拆开后她的断言更强也更可证伪：**"字不再占用内存"＝"每 token 字节预算"从 GB 级压到 MB 级**。

**H-6｜"GPU比CPU快12倍"（经验集:69）**：16.23÷1.37。

**H-7｜H盘（施工件:134、经验集:53）**："768MB/s顺序/4262 IOPS随机｜模型与热数据唯一正确去处"。

**H-8｜G盘（施工件:136）**："机械硬盘｜mmap换页实测拖死速度（2.8→4.7差距的主因之一）｜禁放热数据与模型（知世2026-10-26令）"。

文献：本卷无法核对（平台专属），但第 8 条与硬件有交叉——**`-fa on` 在 Polaris 上是否真生效需要测**（f16/内核可用性见 H-3）；第 10 条（H 盘整盘离线）与§三.5 的"页缓存被冲"是同一风险族。→ **待测（HW-5/HW-6）**。
**H-11｜常驻 3 GB＋"字不再占用内存，家用电脑做出比现在更强的AI"（施工件:26）**。
文献：稀疏激活 MoE 的边缘部署族（EdgeMoE、Fate、DynamicInfer、Prism、DALI）都在做同一件事——**只把被激活的部分搬进快介质**；这与她的"宇宙常驻、生成=查表"同向。→ **对应（占点成立）**；但"更强的AI"这句在硬件层只能是"同一字节预算下域内更强"，不能是通用能力对标——她的§〇.①丑话前置已经自己写过，本卷维持。
**H-12｜生成=查表+图游走 5012 tok/s、27000 步/s（施工件:11/26）**。
算术：按达成带宽 8.7 GB/s 反推，**每 token 触碰 ≈1.7 MB**；27000 步/s＝37 µs/步，这个量级在 RAM-resident 的查表/图游走里属于**软件开销受限**（Python/numpy），不是内存受限——硬件给的是"若 1.7 MB 全在 L3/页缓存热区，本可更快"。→ **对应（速度真实）＋定位改写**：宇宙侧目前不是被硬件咬，是被实现咬；端到端速度由门决定，优化宇宙侧速度对端到端几乎无收益。[T-MAC: CPU Renaissance via Table Lookup for Low-Bit LLM Inference](https://arxiv.org/abs/2407.00088 "qoder-citation:v1")
**H-13｜"设计时速100-1000 tok/s"（施工件:38）**。

**H-14｜判据 JC-C1 ≥2.0 tok/s（施工件:258）**："30B门实测4.7的保守折扣，宇宙查表必须<50ms/步不拖后腿"。
算术：门 4.7 tok/s＝213 ms/token；她的"<50 ms/步"要求≈20 步/s，而她宇宙实测 5012 tok/s（0.2 ms/步）**余量 250 倍**——这条约束现在完全不是瓶颈，真正的瓶颈是门本身；判据应改为**分离口径**（pp 与 tg 分开测、分开给档），否则一个 2.0 tok/s 的合成分辨不出§三.3 的任何机制。→ **对应（可达）＋建议改口径（待令）**。
**H-15｜"两词表线对齐是接入工程的第一个硬件，做不好后面全塌"（施工件:165）**。
文献：跨 tokenizer 的移植/对齐已有方法族（MATT 2025、跨词表似然评分 ICLR'26、trans-tokenization），且这些方法解决的是**语义对齐**，不是她说的"运行时口径"。→ **对应**；但她的用法（V4.1 id 空间的候选要交给 Qwen3 id 空间的门打分）在文献里最贴的锚是"cross-tokenizer likelihood scoring"——它给的是可无损换算的递归算法与更快的近似，可直接借用为对齐验收工具。[Cross-Tokenizer Likelihood Scoring](https://proceedings.iclr.cc/paper_files/paper/2026/file/40d50fe20d5e6922dbb52d7da6de03f1-Paper-Conference.pdf "qoder-citation:v1")

## 三 带宽硬墙算术核验（本卷的硬件本体）

### 3.1 从公开 config 反推她那颗门的每-token 字节量

用 HF 官方 `Qwen/Qwen3-30B-A3B/config.json` 原文值（hidden 2048／48 层／Q 32 头／KV 4 头／head_dim 128／moe_intermediate 768／128 专家／每 token 激活 8 个／vocab 151936／tie_word_embeddings=false）：

| 块 | 参数量 | 每 token 是否读 | Q4_K_M 字节（0.608 B/参数，由她 18.56 GB÷30.53 B 得出＝4.863 bpw） |
|---|---|---|---|
| 路由专家（128×48） | 28.991 B | 只读其中 8 个/层 → 激活 1.812 B | **1.101 GB** |
| attention（Q/K/V/O） | 0.906 B | 全读 | 0.551 GB |
| router | 0.013 B | 全读 | 0.008 GB |
| lm_head（不与 embed 绑定） | 0.311 B | 全读 | 0.189 GB |
| 合计激活 | **3.042 B** | — | **1.849 GB/token** |

三个结论：①她登记的"30.5B 总参/3.3B 激活"与公开 config 算出的 30.53 B/3.04 B 吻合（差 8%，来自 rms_norm 与 embed 行处理的口径），**她的模型描述是真的**；②每 token 必读 1.849 GB，这是任何"速度"的除数；③**lm_head 单独占 0.189 GB/token**（15.19 万词表 ×2048），这是她"两词表线"在硬件上的代价——词表越大，门越慢，与语义无关。

KV 侧：`2×48×4×128×2B`＝**98,304 B/token（0.096 MB）**，16k 上下文＝1.61 GB、4k＝0.40 GB。她实测显存 2.3 GB 与"0.748 GB 权重＋4k KV＋缓冲"自洽。

### 3.2 把她的六个实测数换成"达成带宽"

| 她的实测（原话位置） | 每 token 字节 | 达成带宽 | 占理论比 |
|---|---|---|---|
| 30B 混合 4.7 tok/s（施工件:110/131） | 1.849 GB（CPU 侧 1.101） | **8.69 GB/s** | 22.6%（@38.4）/17.4%（@50） |
| 30B 纯 CPU 4.0–4.3 tok/s（施工件:132） | 1.849 GB | **7.40–7.95 GB/s** | 19.3–20.7% |
| 7B 纯 CPU 1.37 tok/s（经验集:69/77） | 4.08 GB | **5.59 GB/s** | 14.6% |
| 7B RX 580 16.23 tok/s（经验集:68/78） | 4.08 GB | **66.2 GB/s** | 25.9%（@256 GB/s） |
| 552B mmap 流式 <1 tok/s（总索引:124） | ≈4.44 GB（90.8 GB÷552 B×27 B 激活） | <1–4 GB/s（NVMe 档） | 盘速决定，与 DDR 无关 |
| 宇宙查表 5012 tok/s（施工件:11/26） | **反推 ≈1.74 MB/token** | 8.7 GB/s（假定同机 DDR 档） | 见§3.3 |

三条读法：

1. **她所有 CPU 侧数字挤在 5.6–8.7 GB/s 这个窄带里**。她写"各配置速度差异都在误差带内"——不是巧合：她的机器在 CPU 侧的**实际**内存吞吐就是 8–9 GB/s 这个量级，换 offload 配置当然看不出差别，因为改的不是被咬住的那根线。文献给这条窄带的解释族：MoE 专家是**散点读**（每层跳 8 个不连续专家块），DRAM 的 row/bank 命中差、TLB/页表遍历、以及 llama.cpp 每 token 重走 48 层的路由 gather；PowerInfer/EdgeMoE/DALI 全族的存在理由就是"稀疏激活的局部性没被硬件层兑现"。[PowerInfer](https://arxiv.org/html/2312.12456v2 "qoder-citation:v1")
2. **RX 580 那 25.9% 不是病**。256 GB/s 是理论峰值，llama.cpp/GGML Vulkan 在 legacy AMD 上普遍跑在峰值的 20–35%，她的 16.23 tok/s（66.2 GB/s）在社区同代卡的正常带内——**GPU 侧健康，不需要动**。她的 2048SP 比满血少 11% 着色器、FP32 ≈5.26 TFLOPS（2048×2×1284 MHz），而 decode 每 token 只需 6.08 GFLOP，算力上 GPU 有 3 个数量级余量——**GPU 不是墙，一个字都不是**。[Radeon 500 series](https://en.wikipedia.org/wiki/Radeon_500_series "qoder-citation:v1")
3. **PCIe 才是"把专家搬上 GPU"这条路的墙**。RX 580 走 PCIe 3.0 ×16（理论 15.75 GB/s、实用 ~13.5 GB/s），若每 token 把 1.101 GB 专家从 CPU 侧灌进显存，上限只有 **12.3 tok/s**；且 8 GB 显存（或 H-3 的 4 GB 疑云）装不下 17.6 GB 专家。**她"专家留 CPU、attention 上 GPU"的切法在算术上是最优解，不是妥协。**[RX 580 8GB running a 35B MoE model via Vulkan (llama.cpp hybrid fit)](https://www.phoronix.com/forums/forum/linux-graphics-x-org-drivers/vulkan/1641907-rx-580-8gb-running-a-35b-moe-model-via-vulkan-llama-cpp-hybrid-fit "qoder-citation:v1")

### 3.3 一个自洽到可以当验收尺的发现

把§3.2 第 1 行的达成带宽（8.69 GB/s）与宇宙侧的 5012 tok/s 并置：**同一台机器、同一条 DDR，门跑 4.7、宇宙跑 5012，比值 1066；而两者每 token 的字节量比值 1849 MB ÷ 1.74 MB ≈ 1063。两个独立来源的数字在小数点后对上了。**

这不是巧合，这是她的架构断言的硬件真身：**速度差＝每 token 触碰字节差**。所以"5000 倍"不该写成速度倍数，应写成——

> 概念宇宙把每 token 的内存触碰量从 GB 级压到 MB 级（本卷复算 ≈1.7 MB/token），在固定内存吞吐下速度按反比放大。

这一改写有两个好处：①它是**可测的**（HW-2：用性能计数器/页故障计数直接量每步触碰字节，验前预测值 1.74±1 MB/token）；②它把"更强 AI"这句可量化的部分与不可量化的部分分开了——字节预算可测，能力不可测。

### 3.4 "12×（GPU 比 CPU 快）"应改档

诚实口径：GPU 66.2 GB/s ÷ CPU 8.7 GB/s ＝ **7.6×**，再乘 GPU 侧只需搬 0.748 GB、CPU 侧需搬 1.101 GB 的**负载分工差异**，纯器件可比性更弱。她原句保留"加速器不是主引擎"的定位即可，倍数应改。

### 3.5 "2.8→4.7 是 G 盘 mmap 换页"这条她写对了，但还有第二段

同一机制在她当前配置里还没关：H 盘 17.5 MB/s 的随机 4K 档意味着**只要有任何一段权重没在页缓存里，散读就会把 8.7 GB/s 打到 17.5 MB/s**。上游报告里"长 prompt 冲掉页缓存、之后生成变慢"就是这一条的运行时形态，而她的 `-c 16384`＋24 GB 内存（模型 18.56 GB＋KV 1.61 GB＋宇宙 3 GB＋系统与驱动常驻＋llama 缓冲）已经在**恰好没有余量**的位置。文献同族的量化口径：FlexGen 用线性规划在 GPU/CPU/盘之间排负载，结论就是当盘进入关键路径时吞吐由 IO 而非算力决定；ktransformers 侧的社区报告同样显示移动端 16 GB VRAM 跑 ~30B 时线程超配与 offload 组合能把速度打到 18 t/s 档。[FlexGen: High-Throughput Generative Inference with a Single GPU](https://arxiv.org/html/2303.06865 "qoder-citation:v1")

### 3.6 速度档位的物理路径（把"100-1000 tok/s"落到算术上）

公式：`tok/s ≈ 达成带宽 × L ÷ 1.849 GB`，L＝每次前向被接受的 token 数（投机解码口径；L=1 即自回归）。

| 条件 | 达成带宽 | L | 预期 |
|---|---|---|---|
| 她现状 | 8.7 GB/s | 1 | **4.7 tok/s**（实测吻合） |
| 只修效率（mlock/容量/线程/关 SMT） | 19.2 GB/s（50%） | 1 | 10.4 |
| 修效率＋宇宙当草稿器 | 19.2 GB/s | 3 | **31** |
| 修效率＋L=5（文献上限档） | 19.2 GB/s | 5 | **52** |
| 30B 门要上 100 | 19.2 GB/s | **需 9.6** | 文献接受长度典型 2–4 → 不成立 |
| 7B 门（4.08 GB）＋L=3、GPU 66 GB/s | 66 GB/s | 3 | **48** |
| 7B 门＋L=6 | 66 GB/s | 6 | **97 ≈ 100** |

**结论：她的"设计时速 100–1000"要按门重排**——30B 门在 24 GB 家用机上的诚实档是 10–50 tok/s（且需要两项同时成立：内存吞吐修到 50%、宇宙做草稿器）；100 tok/s 档只有 7B 门＋投机或更小门可达；1000 tok/s 在这台机器上任何"要读全激活权重的门"上都不成立，只有"门不逐 token 参与"（宇宙自出终稿＋抽检）才在字节预算上成立。

## 四 文献比她强、可以直接借的三条（都带硬件收益预估）

1. **宇宙＝现成的草稿器，门＝验证器；这是投机解码，不是新东西，但她有别人没有的草稿源。** 文献口径：验证 K 个草稿 token 与验证 1 个 token 的**权重读量几乎相同**，所以参数读被摊销——MoE 场景专门有一篇讲这个成本模型（Cost-Aware Speculative Decoding for MoE）；无模型的草稿替代方案里，**后缀树/历史续写草稿（SuffixDecoding，vLLM 已并入）**最贴她的"转移谱+trigram+哈密顿游走"，因为这类草稿器零内存读、零权重、纯索引。她的 5012 tok/s 查表速度相对门的 213 ms/token 有 250 倍余量，正好可以在一次门前向里塞 3–5 个候选。**收益见§3.6；成本：不改硬件、只改编排；风险：接受率低时更慢（MLSys'26 有专门一文题为《Speculative Decoding: Performance or Illusion?》）。** [Suffix Decoding (vLLM docs)](https://docs.vllm.ai/en/stable/features/speculative_decoding/suffix/ "qoder-citation:v1")
2. **CPU 侧不只能做"查表"，还能做"免解包计算"——但她缺指令集，这条要诚实降级。** T-MAC 把低位权重推理改成**查找表（LUT）mpGEMM**，主张 CPU 复兴，且直接支持 gguf 的 W4A16；LUT Tensor Core 把同一想法做到加速器侧。KTransformers（SOSP'25）的融合 MoE kernel 走 AVX-512/AMX。**她的 Zen2 只有 AVX2 → T-MAC 的 AVX2 后端可用、AMX 不可用**；这条给她的不是"翻倍"，是"把 CPU 侧从 dequant+dot 的访存模式换成 gather 查表"的中等收益（文献自报为数倍级，非数量级）。[T-MAC](https://arxiv.org/abs/2407.00088 "qoder-citation:v1")
3. **容量优先于频率：正确的采购档是 2×32 GB，不是她写的 2×16 GB。** 理由全在§3.5 的余量算术：18.56（模型）＋3（宇宙常驻）＋1.6（16k KV）＋驱动/系统/缓冲 ≈ 26–27 GB，**32 GB 只有 5–6 GB 余量，仍然贴着悬崖**；而一次 prefill 扫全 128 专家的足迹是 17.6 GB，与模型常驻等量——这就是 `pp=tg` 的候选机制。**64 GB 才让 prefill 不再自噬页缓存。** 收益预估：如果机制成立，pp 从 4.7 走到 20–40 tok/s（文献同型：4.6→16.3/48.4/117.5/140.3），比单纯换高频内存的 1.33× 大得多。[Slow prompt processing when MoE experts are read from disk via mmap](https://github.com/ggml-org/llama.cpp/issues/29130 "qoder-citation:v1")

## 五 冲突点与风险（逐条给可证伪测试）

1. **`内存 ~50 GB/s`（经验集:56）与 `DDR4-2400 双通道理论 38.4 GB/s` 不相容。** 50 GB/s 只有在 2666（42.7）以上、或 3200（51.2）才可能。要么她的实际运行频率不是 2400（BIOS 读回为准），要么这条是从别的工具/单位抄来的（例如 50,000 MB/s 被写成 50 GB/s 时反而吻合 2666）。**HW-4：CPU-Z/AIDA 读回真实 MEMCLK 与通道状态，再用内存带宽实测三档（读/拷贝/混合）。**
2. **`pp=tg=4.7` 与文献"prefill 算力受限、decode 带宽受限"的分离结论冲突。** 她的 CPU 侧算力上限复算为 ≈25 tok/s（384 GFLOPS 峰、40% 实效率、6.08 GFLOP/token）——**她的 4.7 比算力墙慢 5.3×**，说明限制来自第三条线（页缓存/散读）。**HW-1：同模型、同参数，分别跑 32/256/2048/8192 token 的 prompt，记录 pp 与 tg 两栏；若 pp 随长度上升而 tg 不变 → 权重读摊销机制确认；若两者都随长度崩塌 → 页缓存被冲机制确认。** 判据预注册（先看数再判，遵守她的冻结书制度）。
3. **`加内存条翻倍以上`（施工件:263）与纯带宽算术（+33%）冲突。** 可同时成立的唯一路径是"当前工作集部分落在 flex 单通道溢出区或正被换页"。这条与第 2 条共用 HW-1/HW-4 的数据即可裁决，**不需要先花钱**。
4. **`-fa on` 与 Polaris 的 f16 能力存疑冲突。** 社区同时存在"RX 580 的 Vulkan 驱动报告不支持 Float16"的提问与 RX 580 跑 LLM 的正常实录；若 f16 kernel 不可用，flash-attn 路径可能静默降级。**HW-5：抓 llama-server 启动日志的 ggml_vulkan 设备能力段，记录 f16 支持位、可用显存字节数（对照 8 GB 与"4 GB 疑云"）、以及 `-fa on` 是否被接受并生效。**
5. **`2048SP 只有 4 GB VRAM`（经验集:70）与 `8 GB`（施工件:131）自相矛盾**，且第 4 条社区报告支持"Vulkan 只吃到约 4 GB"这一解释。**若成立：她想"多上显存"的路有硬顶，必须走 Vulkan 之外的后端（OpenCL/RADV 参数）或接受显存路线不可扩展。** 与 HW-5 同一实验解决。
6. **口径不公平仍在档**：`5012 对 <1` 的 5000×（§〇.5 已拆）；`12×`（§3.4 已改 7.6×）。这两条不是错误，是**登记口径**问题，建议正本按本卷改注。
7. **质量与速度不能同档比**：本卷全部是速度/器件结论，**不涉及任何"更强"的质量结论**；她的四臂实验（A kNN 插值 logprob −1.254 对纯 LM −1.448）仍是我能见到的最好质量证据，但那是她批 3 的口径，本卷不重复背书。
