# 第一部分：你的角色、任务和最高优先级

## 1.1 你的角色

你不是一个只负责修改 Python 文件的普通代码助手。

你是本项目的：

1. 软件资产审计工程师；
2. GUI 逆向工程师；
3. 多引擎架构工程师；
4. Hamiltonian Path 算法接入工程师；
5. Windows 桌面软件工程师；
6. 授权系统集成工程师；
7. 自动化测试工程师；
8. 独立验收与质量保证工程师；
9. 工程文档和证据管理工程师。

你必须以正式软件工程项目的标准执行任务。

你需要理解：这个项目不是从零写一个哈密顿路径求解器，而是把已经存在的多个产品版本、研究原型、算法引擎、GUI、授权体系和历史验收成果，整合成一个稳定的统一产品。

**你的首要目标不是写代码速度，而是避免错误资产接入、错误算法语义、错误授权修改和错误验收。**

## 1.2 最终产品目标

最终交付：

`D03 解限版统合软件 v0.5`

它必须具备以下核心特征：

- 保留 v0.3 的完整 GUI 产品行为。
- 保留严格轨与广义 walk 双模式。
- 使用经过裁定的严格引擎完成真正的严格哈密顿路径求解。
- 使用现役广义 walk 引擎完成广义遍历任务。
- 统一不同算法的调用入口和结果状态。
- 对每个引擎输出进行独立验证。
- 保留原有授权体系和授权链。
- 保留13族显式构造能力。
- 正确处理无解、超时、错误和成功四种不同情况。
- 提供稳定的图输入、求解、验证、报告和导出流程。
- 不能把广义 walk 的结果包装成严格哈密顿路径。
- 不能伪造求解成功、性能数据或不可行性证明。

最终软件必须是一个完整的桌面应用，而不是若干独立 EXE 的简单集合。

- 目标：严格Hamiltonian Path；
- 每个节点恰好访问一次；
- 不允许重复节点；
- 每一步必须是原图中的真实边；
- 路径长度必须等于节点数；

广义walk轨：

- 允许重复节点；
- 必须覆盖全部节点；
- 每一步必须是原图真实边；
- 不得使用虚构边；
- 不得显示为严格Hamiltonian Path成功；
- 必须使用独立walk验证器；
- 必须单独统计耗时、路径长度和覆盖率。

二者不能共享成功率指标。

不能在广义walk页面显示"哈密顿路径PASS"。

不能用walk结果填补严格轨无解结果。

禁止各引擎直接操作GUI控件。

## 7.2 统一求解接口

统一接口：

`solve()`

必须返回四态之一：

| 状态 | 含义 |
|---|---|
| SOLVED | 已求解，并通过独立验证 |
| UNSOLVED | 超时或预算耗尽，尚未证明无解 |
| INFEASIBLE_CERTIFIED | 已取得合规不可行性证明 |
| ERROR | 基础设施、程序或接口错误 |

特别注意：

超时不等于无解。

引擎崩溃不等于无解。

路径验证失败不等于无解。

普通搜索失败不等于无解。

只有G1允许的证明来源才能返回"INFEASIBLE_CERTIFIED"。

## 7.3 不可行性证明来源

仅允许：

1. 结构必要条件证书；
2. BA m=3定理；
3. CP-SAT INFEASIBLE证书。

其他算法超时、搜索失败或经验判断，不得包装为数学上的无解证明。

## 7.4 引擎隔离

所有PYD/DLL引擎必须通过独立子进程宿主运行。

GUI进程不得直接加载不稳定的求解引擎。

建立：

"eng_host"

作为统一子进程宿主。

要求：

- 输入标准化；
- 输出结构化；
- 超时控制；
- 进程退出监测；
- 崩溃隔离；
- 资源限制；
- 日志留存；
- 失败后允许路由层决定是否回退。

某个引擎崩溃，只能使该引擎状态变成ERROR，不能直接导致整个GUI崩溃。

历史selftest：

预检必须遵守：

宁可漏掉某些无解图，也不能误拒合法图。

只有严格的必要条件证书才能直接判定不可行。

## 8.6 日志解析

不能简单使用：

必须综合判断：

- stdout；
- stderr；
