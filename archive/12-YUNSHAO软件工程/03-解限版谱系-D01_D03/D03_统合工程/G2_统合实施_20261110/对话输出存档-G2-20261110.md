## 第 1 条 · 2026-11-10 · G2-A 严格引擎实测结果汇报（对话原文）

引擎实测做完了，结论：**这个引擎能用，但接进软件时必须给它兜底六处毛病。**

先说数字。这次一共跑了 33 个用例，主轮只花 70 秒。核心成绩：每个点连 10 条线的随机图，从 20 个点一直到 1000 个点、换 4 个随机种子，17 张图全部秒出合法路径（每张不到 0.05 秒），而且每一条路径都由独立的检查器重新验过——一个不漏、一个不重、每一步走的线都真实存在，17 条全过。另外用边表文件喂图的通道也验通了：环图、链图、两个三角形一座桥的图都能正确解出。

抓出来的六处毛病（都有存证，写壳的时候必须处理）：

1. 第一个参数不是数字就直接崩溃；
2. 空文件、断开的图这类坏输入不检查，直接崩；
3. 无解的图会把时间预算烧光，还写出一条不合法的路径文件，退出码照样是 0——所以判断成功只能看它自己报的"strict=YES"加独立复核，绝不能看退出码或文件在不在；
4. 不加导出参数就拿不到路径，所以每次调用必须带上；
5. 没有预检，星形图这种一眼无解的也白烧 60 秒——无解判定要在调它之前做；
6. 日志中途会打"ERROR"字样但最后结果可能合法，不能凭日志文字判失败。

纪律账：跑前判据已冻结、跑后复核没漂移；引擎本体跑前跑后哈希一致，一个字节没动；授权、源码、旧版正本全部没碰。写入卫生自查过，本轮新写的四个文件零隐形字节。

## 缺陷一：第一个参数不是数字会直接崩溃

### 问题

严格引擎收到非法第一个参数时会直接崩溃。

### 软件层要求

调用引擎前必须完成输入校验。

检查：

- N 是否存在。
- N 是否为整数。
- N 是否在允许范围。
- seed 是否符合参数要求。
- m 是否符合参数要求。
- 是否存在空字符串。
- 是否存在非数字内容。
- 参数之间是否存在逻辑矛盾。

非法输入不得启动引擎。

### 必须测试

至少覆盖：

- 空输入。
- 字母。
- 小数。
- 负数。
- 极大数字。
- 混合字符。
- 缺失参数。

### 通过标准

所有非法输入均由 GUI 或适配器提前拒绝。

不得出现引擎崩溃。

---

## 缺陷二：空文件、断开的图等坏输入不检查，直接崩溃

### 问题

引擎没有足够可靠的输入图合法性检查。

### 软件层要求

图文件必须在调用引擎之前进行标准化和校验。

至少检查：

1. 文件是否存在。
2. 文件是否可读。
3. 文件是否为空。
4. 节点数是否有效。
5. 边数据是否符合格式。
6. 是否存在非法节点编号。
7. 是否存在自环。
8. 是否存在重复边。
9. 是否存在越界边。
10. 是否存在不连通情况。

注意：

具体图格式、允许的边类型和标准化规则必须依据 G1 设计及 G2-A 实测报告，不得自行改变图语义。

### 结构预检

必须复用或对照 G1 中的结构预检。

至少关注：

- 空图。
- 不连通图。
- 度为 1 的叶节点数量。
- 桥边。
- 桥缩块后的奇度块数量。

结构预检必须保守。

只有符合 G1 允许的必要条件证书，才能判定 INFEASIBLE_CERTIFIED。

不符合证书条件时，不得武断判定无解。

### 必须测试

- 空图。
- 空文件。
- 单节点图。
- 两个互不相连的分量。
- 星形图。
- 两三角形一座桥。
- 含非法节点编号的图。
- 含重复边的图。
- 格式错误的图。

### 通过标准

坏输入在引擎启动前被拦截。

合法输入不会被过度预检错误拒绝。

“两三角形一座桥”的既有回归锚必须继续通过。

---

## 缺陷三：无解图烧光预算，还可能输出非法路径，退出码仍为 0

### 问题

引擎可能：

- 没找到合法路径。
- 烧光时间预算。
- 写出一份非法路径文件。
- 退出码仍然为 0。

所以退出码为 0 不代表求解成功。

路径文件存在也不代表成功。

### 软件层强制要求

判断成功必须同时满足：

1. 引擎输出协议明确报告 `strict=YES`。
2. RESULT 信息能够被正确解析。
3. 路径文件能够被正确读取。
4. 独立严格裁判验证通过。

严格裁判必须检查：

- 路径长度等于 N。
- 节点没有重复。
- 全部节点完整。
- 每一步均为原图真实边。

只要其中一项不通过，就不能返回 SOLVED。

如果引擎报告成功但独立验证失败：

- 记录引擎输出。
- 记录失败路径。
- 记录失败边。
- 标记为 ERROR 或按 G1 状态定义处理。
- 不得将其标记为 SOLVED。
- 不得伪造合法路径。

如果引擎没有找到解或预算耗尽：

- 返回 UNSOLVED。
- 不得返回 INFEASIBLE_CERTIFIED。

### 输出文件防污染

每次求解必须使用独立临时目录或唯一输出文件名。

不得复用上一次求解的路径文件。

必须避免：

- 上一次成功文件被误认成这次结果。
- 失败时遗留旧文件。
- 多个并发任务覆盖同一个输出文件。

### 必须测试

- 已知有解图。
- 已知无解图。
- 超时图。
- 伪造或残留路径文件。
- 引擎报告 strict=YES 但路径非法的模拟情况。
- 退出码为 0 但没有合法路径的情况。

### 通过标准

任何不合法路径都无法进入 SOLVED。

---

## 缺陷四：不加导出参数就拿不到路径

### 问题

引擎不一定默认导出路径。

### 软件层要求

每次严格引擎调用都必须使用 G2-A 实测确认的路径导出参数。

不得依赖默认行为。

必须检查：

- 导出参数是否成功传入。
- 路径文件是否生成。
- 文件是否属于当前任务。
- 文件是否可读取。
- 路径文件是否符合格式。
- 文件是否包含全部必要节点。

### 必须测试

至少执行：

- 一次正常路径导出。
- 一次连续两次不同任务导出。
- 一次前次成功、后次失败。
- 一次路径文件读取异常。

### 通过标准

每次任务都能准确关联自己的输出文件。

---

## 缺陷五：没有预检，星形图等明显无解图会浪费预算

### 问题

明显不满足严格哈密顿路径必要条件的图，仍可能进入引擎搜索并消耗大量预算。

### 软件层要求

引擎调用之前必须进行结构预检。

至少包括 G1 已明确的必要条件。

例如：

- 不连通图。
- 孤立节点。
- 度为 1 的叶节点超过 2 个。
- 桥缩块结构违反必要条件。

但必须遵守：

**预检只允许使用已经证明的必要条件。**

不能把某种经验规律写成数学证书。

### 必须测试

- 星形图。
- 不连通图。
- 三个以上叶节点。
- 两三角形一座桥。
- 普通连通图。
- 随机稠密图。

### 通过标准

明显不可能的图在启动引擎前被正确处理。

合法图不得被错误拒绝。

---

## 缺陷六：日志中途出现 ERROR，但最后可能有合法结果

### 问题

引擎日志中途可能打印：

`ERROR`

但最终仍然可能产生合法结果。

因此，不能简单地使用：

```python
if "ERROR" in stdout:
    fail()
```

这种判断。

### 软件层要求

必须分别保存：

- stdout。
- stderr。
- 进程退出码。
- RESULT 行。
- VERIFY 行。
- 路径文件。
- 独立裁判结果。

最终状态必须由结构化结果和独立裁判共同决定。

不能仅凭日志中出现 ERROR 就直接认定失败。

同样，也不能因为日志中没有 ERROR 就认定成功。

### 必须测试

至少准备：

- 中途出现 ERROR、最终合法。
- 中途没有 ERROR、最终非法。
- 有 RESULT、没有 VERIFY。
- 有 VERIFY、没有路径文件。
- 输出格式不完整。
- 进程异常退出。

### 通过标准

日志文字不再成为单独的成功或失败判据。

# 第七章：严格引擎适配器设计

## 7.1 独立适配器

建立严格引擎适配器。

建议：

`engine/strict_adapter.py`

其职责是：

1. 接收标准化图。
2. 校验参数。
3. 运行结构预检。
4. 创建独立任务目录。
5. 构造 CLI 参数。
6. 启动严格引擎。
7. 捕获 stdout。
8. 捕获 stderr。
9. 控制时间预算。
10. 收集输出文件。
11. 解析 RESULT。
12. 解析 VERIFY。
13. 读取路径。
14. 调用独立裁判。
15. 返回统一四态结果。

GUI 不得直接执行以上所有步骤。

## 7.2 适配器输入

必须定义清晰的输入接口。

例如：

```python
solve_strict(
    graph,
    seed,
    budget,
    output_dir
)
```

这是接口设计示例。

具体参数必须与实际 G2-A 测试报告一致。

## 7.3 适配器输出

建议统一结构：

```python
{
    "status": "SOLVED",
    "engine": "strict_17_10",
    "path": [],
    "metrics": {},
    "verification": {},
    "stdout_file": "",
    "stderr_file": "",
    "report_file": "",
    "error": None
}
```

字段可以按 G1 统一接口调整，但不能遗漏：

- 四态状态。
- 引擎标识。
- 路径。
- 指标。
- 验证结果。
- 原始日志位置。
- 错误信息。

## 7.4 解析规则

必须使用 G2-A 已验证的真实输出协议。

不能只用简单字符串搜索。

需要对 RESULT 和 VERIFY 进行结构化解析。

处理：

- 缺失字段。
- 重复字段。
- 非法数字。
- 格式错误。
- 多余输出。
- 编码异常。
- 不完整输出。

无法解析时必须明确报告，不能猜测。

## 7.5 时间预算

时间预算由上层传入。

不得在适配器里擅自把预算无限放大。

超时后：

- 终止当前进程。
- 保存日志。
- 保存任务信息。
- 返回 UNSOLVED 或按 G1 规定的异常状态处理。
- 不得宣称无解。

## 7.6 并发

每个任务必须独立：

- 临时目录。
- 输出文件。
- 日志文件。
- 进程句柄。
- 超时控制。

不得让两个求解任务共享路径输出文件。

# 第八章：GUI 与严格/广义两条轨道的隔离

## 8.1 严格轨

严格轨显示：

- 严格求解模式。
- 节点数。
- 随机种子。
- 图来源。
- 运行预算。
- 当前状态。
- 严格路径。
- 独立验证结果。
- 导出位置。

只有独立验证通过才能显示成功。

## 8.2 广义轨

广义轨显示：

- 广义 walk 模式。
- 节点覆盖情况。
- 重复访问情况。
- 步数。
- 断边数量。
- 独立 walk 验证结果。

不得将广义 walk 结果显示成严格哈密顿路径。

## 8.3 UI 文案隔离

以下文案必须严格区分：

严格成功：

`严格哈密顿路径验证通过`

广义成功：

`广义覆盖 walk 验证通过`

广义结果不能出现：

`Hamiltonian Path PASS`

不能把两种模式的节点数、步数、路径长度、成功率放在同一个指标中混算。

## 8.4 状态颜色与图标

可以沿用 v0.3 的 UI 风格。

但颜色不能替代状态文字。

至少明确区分：

- 求解中。
- 已验证成功。
- 未找到解。
- 已认证无解。
- 系统错误。
- 等待授权。

```python
def solve_strict(graph):
```

```python
def solve_strict(graph):
    """
    Strict solver adapter interface.

    Actual engine integration is deferred to Batch 6.
    """
    raise NotImplementedError(
        "Strict engine integration is not implemented in Batch 1."
    )
```

同样的原则适用于：

- 授权验证。
- 路径验证。
- 图预检。
- 广义 walk。
- 报告导出。
- 引擎路由。

```python
from enum import Enum

class SolveStatus(str, Enum):
```

# 第七部分：架构边界检查

本批次必须提前建立架构约束测试，防止后续开发逐渐失控。

## 7.1 GUI 边界

GUI 模块不得：

- 直接调用严格引擎 EXE。
- 直接加载 walk DLL。
- 直接解析 RESULT 和 VERIFY。
- 直接实现图算法。
- 直接实现独立路径裁判。
- 直接修改授权状态。

GUI 只能通过设计规定的接口调用业务模块。

## 7.2 授权边界

`auth_bridge.py` 只能作为现有授权接口的薄桥接层。

本批次：

- 不导入并执行真实授权流程。
- 不重写授权核心。
- 不生成授权 token。
- 不读取或打印敏感 token 内容。
- 不修改 auth.pyd。
- 不修改六件授权伴生。

真实授权接口接线留在后续规定批次。

## 7.3 引擎边界

本批次：

- 不启动任何引擎。
- 不加载任何 DLL。
- 不执行任何求解。
- 不建立真实子进程调用。
- 不构造真实 CLI 命令。

仅建立接口和职责边界。

## 7.4 验证边界

严格验证和广义验证必须是两个独立接口。

不能建立一个含糊的 `validate_path()` 函数同时处理两种语义，除非审核设计明确规定其为共享底层工具，且两种验证规则仍然独立。

## 7.5 依赖方向

依赖必须符合审核设计的十层架构。

禁止：

- UI 反向依赖具体引擎实现。
- 引擎模块直接依赖 UI。
- 验证模块依赖 GUI 控件。
- 授权模块依赖求解器。
- 底层图模块依赖上层窗口。

如果发现循环依赖，必须修正目录和接口设计，不得通过随意添加 `sys.path` 或延迟导入掩盖问题。
